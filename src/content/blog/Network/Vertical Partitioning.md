## 1. 논리 계층과 실제 서버는 같은 개념이 아니다

웹 애플리케이션은 화면을 제공하고, 요청을 처리하며, 데이터를 저장한다. 이 역할을 설명할 때 프레젠테이션 계층, 애플리케이션 계층, 데이터 계층처럼 논리적인 계층으로 나눌 수 있다.

```text
Presentation
    ↓
Application
    ↓
Data
```

논리 계층을 세 개로 나눴다고 반드시 서버도 세 대가 필요한 것은 아니다. 하나의 서버 안에서 세 역할을 모두 실행할 수도 있고, 계층마다 여러 서버와 관리형 서비스를 배치할 수도 있다.

```text
논리 구조: 역할을 어떻게 나누는가
배포 구조: 그 역할을 어디에서 실행하는가
```

이 둘을 구분해야 `Controller`, `Service`, `Repository`를 나눴다는 이유만으로 3계층 인프라를 구축했다고 표현하거나, 서버를 여러 대 사용한다는 이유만으로 책임이 잘 분리됐다고 판단하는 오류를 피할 수 있다.

## 2. 한 서버 구성은 단순한 출발점이다

작은 서비스나 학습용 프로젝트는 웹 서버, 애플리케이션과 데이터베이스를 한 서버에서 실행할 수 있다.

```text
사용자
  ↓
하나의 서버
  ├── Nginx
  ├── Spring Boot
  └── MySQL
```

이 구성은 배포 대상과 네트워크 연결이 적어 시작하기 쉽다. 한 서버의 로그와 프로세스만 확인하면 되므로 초기 운영도 단순하다. 별도의 데이터베이스 서버나 로드 밸런서 비용도 들지 않는다.

대신 서버 한 대의 장애가 전체 서비스 장애로 이어진다. 애플리케이션의 CPU 사용량이 급증하면 같은 서버의 데이터베이스도 영향을 받을 수 있고, 애플리케이션만 여러 대로 늘리고 싶어도 구성 요소가 한곳에 묶여 있어 분리 작업이 필요하다.

한 서버 구성이 잘못된 구조인 것은 아니다. 다음 조건이라면 합리적인 선택이 될 수 있다.

* 사용량이 작고 장애 시 복구 시간을 감당할 수 있다.
* 운영 인력과 비용이 제한적이다.
* 데이터베이스와 애플리케이션을 분리해야 할 근거가 아직 없다.
* 백업과 복구 절차를 별도로 마련했다.

구조를 단순하게 유지하는 대신 장애 범위와 자원 경쟁을 받아들이는 선택이다.

## 3. 3계층 구조는 역할별 경계를 배포에 반영한다

일반적인 3계층 웹 아키텍처는 프레젠테이션, 애플리케이션과 데이터 계층을 구분한다.

```text
사용자
  ↓
프레젠테이션 계층
  ↓
애플리케이션 계층
  ↓
데이터 계층
```

### 3.1 프레젠테이션 계층

사용자의 요청을 가장 먼저 받는 영역이다. 정적 파일을 제공하거나 TLS를 종료하고, 요청을 애플리케이션 서버로 전달할 수 있다.

예시는 다음과 같다.

* 브라우저에서 실행되는 React 애플리케이션
* 정적 파일을 제공하는 CDN과 오브젝트 스토리지
* Nginx 같은 리버스 프록시
* 여러 애플리케이션 서버로 요청을 분배하는 로드 밸런서

프레젠테이션 계층을 별도로 둔다고 모든 구성이 필요한 것은 아니다. 서버 렌더링 애플리케이션 하나만 운영한다면 Spring Boot가 HTML 응답까지 담당할 수 있다.

### 3.2 애플리케이션 계층

요청을 해석하고 서비스 규칙을 실행한다. Spring Boot 애플리케이션에서는 컨트롤러, 서비스와 데이터 접근 코드가 이 계층 안에서 동작할 수 있다.

```text
HTTP 요청
  → Controller
  → Service
  → Repository
```

애플리케이션 서버를 여러 대로 늘리려면 각 인스턴스가 가능한 한 동일한 요청을 처리할 수 있어야 한다. 세션이나 업로드 파일을 로컬 디스크에만 저장하면 요청이 다른 인스턴스로 전달될 때 문제가 생길 수 있으므로 공유 저장소나 세션 전략을 함께 검토해야 한다.

### 3.3 데이터 계층

애플리케이션의 영속 데이터를 저장한다. MySQL 같은 관계형 데이터베이스, Redis와 오브젝트 스토리지 등이 이 영역에 포함될 수 있다.

데이터 계층을 애플리케이션 서버와 분리하면 자원을 독립적으로 관리하고 접근 경로를 제한하기 쉽다. 그러나 네트워크 지연과 연결 실패 가능성이 추가되며, 데이터베이스 자체의 백업·복제·장애 조치 전략도 필요하다.

## 4. 서버를 나누는 것만으로 가용성이 생기지는 않는다

한 서버를 웹 서버, 애플리케이션 서버와 데이터베이스 서버 세 대로 나누면 역할별 자원 경쟁은 줄일 수 있다. 그러나 각 계층에 서버가 한 대뿐이라면 여전히 그 서버가 단일 장애 지점이다.

```text
Load Balancer 1대
Application 1대
Database 1대
```

이 구조는 물리적으로 분리됐지만 어느 한 구성 요소가 중단되면 전체 요청 흐름이 끊길 수 있다. 가용성을 높이려면 분리 외에도 다음 조건이 필요하다.

* 애플리케이션 인스턴스의 복제와 헬스 체크
* 요청을 분산하는 로드 밸런서
* 데이터베이스 백업과 복구 절차
* 필요하다면 데이터베이스 복제와 자동 장애 조치
* 로그, 메트릭과 알림
* 배포 실패 시 되돌릴 수 있는 절차

분리는 확장과 장애 격리의 기반을 제공하지만, 중복 구성과 복구 절차가 있어야 실제 가용성으로 이어진다.

## 5. 수직 확장과 수평 확장을 구분한다

배포 구조를 확장하는 방법은 크게 두 가지다.

<!-- table-caption: 수직 확장과 수평 확장의 차이 -->

| 구분 | 방식 | 확인할 점 |
| --- | --- | --- |
| 수직 확장 | 한 서버의 CPU, 메모리와 저장 장치 성능을 높인다. | 구조가 단순하지만 장비 한계와 단일 장애 지점이 남는다. |
| 수평 확장 | 같은 역할의 서버 인스턴스를 여러 개 둔다. | 로드 밸런싱, 상태 공유와 데이터 일관성을 검토해야 한다. |

애플리케이션 서버를 여러 대로 늘리는 것은 수평 확장이다. 데이터베이스가 같은 서버에 묶여 있으면 애플리케이션만 독립적으로 늘리기 어려우므로 역할별 분리가 확장의 전제가 될 수 있다.

파일명에 남아 있는 `Vertical Partitioning`은 이 글에서 설명하는 역할별 계층 분리와 정확히 같은 표준 용어가 아니다. 데이터베이스의 수직 파티셔닝은 한 테이블의 열을 나누는 설계를 가리킬 수 있고, 수직 확장은 한 서버의 사양을 높이는 방식이다. 이 글은 웹 애플리케이션의 역할을 계층으로 나누고 실제 배포 단위를 선택하는 문제에 집중한다.

## 6. 규모보다 운영 요구로 구조를 선택한다

처음부터 모든 계층을 여러 대로 구성하면 장애 격리와 확장 선택지는 늘어나지만 배포, 네트워크, 보안, 모니터링과 비용도 함께 복잡해진다.

구조를 선택할 때는 예상 사용자 수 하나보다 다음 질문이 더 직접적인 기준이 된다.

* 어느 정도의 중단 시간을 허용할 수 있는가?
* 애플리케이션과 데이터베이스 중 어느 자원이 먼저 부족해지는가?
* 특정 계층만 독립적으로 배포하거나 확장해야 하는가?
* 운영자가 장애 원인을 찾고 복구할 수 있는가?
* 데이터 백업과 복구 목표가 정해져 있는가?

작은 프로젝트는 한 서버에서 시작하고 측정 결과와 운영 요구가 생길 때 데이터베이스, 리버스 프록시와 애플리케이션 인스턴스를 단계적으로 분리할 수 있다. 중요한 것은 서버 수가 아니라 분리로 해결하려는 문제가 명확한지 확인하는 것이다.

## 7. 정리

* 논리 계층은 역할을 나누는 기준이고 배포 구조는 그 역할을 어디에서 실행할지 정하는 문제다.
* 한 서버 구성은 초기 비용과 운영 복잡도가 낮지만 자원 경쟁과 단일 장애 지점을 감수해야 한다.
* 3계층 구조는 프레젠테이션, 애플리케이션과 데이터 역할을 분리해 독립적인 운영과 확장의 기반을 제공한다.
* 서버를 여러 대로 나누는 것만으로 가용성이 보장되지는 않으며 복제, 헬스 체크, 백업과 복구 절차가 함께 필요하다.
* 인프라는 규모만으로 결정하지 않고 허용 가능한 장애 시간, 자원 병목, 배포와 운영 역량을 기준으로 단계적으로 분리한다.
