## 1. 영속성 컨텍스트가 엔티티를 관리한다는 것

JPA에서 엔티티를 저장하고 조회하는 동작은 영속성 컨텍스트를 중심으로 이루어진다. 영속성 컨텍스트(Persistence Context)는 **엔티티를 관리하는 논리적인 공간**이며, 애플리케이션은 `EntityManager`를 통해 이 공간에 접근한다.

객체를 생성했다고 해서 바로 JPA의 관리 대상이 되는 것은 아니다. 아직 영속성 컨텍스트와 관계가 없는 객체를 **비영속(new/transient)** 상태라고 한다. 이후 `persist()`를 호출하면 엔티티가 영속성 컨텍스트에 등록되고 **영속(managed)** 상태가 된다.

엔티티의 상태는 크게 네 가지로 나뉜다.

- **비영속**: 영속성 컨텍스트와 관계가 없는 상태
- **영속**: 영속성 컨텍스트가 관리하는 상태
- **준영속**: 관리되던 엔티티가 영속성 컨텍스트에서 분리된 상태
- **삭제**: 삭제 대상으로 등록된 상태

![엔티티 생명주기](<스크린샷 2026-08-20 150056.png>)

준영속 상태로 만드는 대표적인 방법에는 `detach()`, `clear()`, `close()`가 있다. `detach()`는 특정 엔티티만 분리하고, `clear()`는 현재 영속성 컨텍스트가 관리하던 엔티티를 모두 분리한다. `close()`는 영속성 컨텍스트 자체를 종료한다.

중요한 점은 JPA의 상태 관리 기능이 **영속 상태의 엔티티를 중심으로 동작한다는 것**이다. 1차 캐시와 변경 감지도 결국 영속성 컨텍스트가 엔티티를 계속 추적하고 있기 때문에 가능한 기능이다.

## 2. 1차 캐시는 왜 필요한가

영속성 컨텍스트는 자신이 관리하는 엔티티를 **1차 캐시**에 보관한다. `find()`로 엔티티를 조회할 때 먼저 1차 캐시를 확인하고, 원하는 엔티티가 없다면 DB에서 조회한 뒤 그 결과를 1차 캐시에 저장한다.

따라서 같은 영속성 컨텍스트 안에서 같은 식별자를 다시 조회하면 DB에서 매번 새로운 객체를 만드는 것이 아니라 이미 관리 중인 객체를 반환할 수 있다.

```java
Member a = em.find(Member.class, "member1");
Member b = em.find(Member.class, "member1");

System.out.println(a == b); // true
```

![1차 캐시](<스크린샷 2026-08-20 150132.png>)

이 때문에 같은 영속성 컨텍스트에서 같은 식별자로 조회한 엔티티는 객체의 동일성도 유지된다.

1차 캐시를 단순한 조회 성능 최적화로만 보면 부족하다. JPA가 같은 엔티티를 하나의 객체로 관리해야 이후 값이 변경되었을 때도 상태 변화를 일관되게 추적할 수 있다.

## 3. SQL을 바로 실행하지 않아도 되는 이유

영속성 컨텍스트는 엔티티의 상태뿐 아니라 DB에 반영해야 할 변경 작업도 관리한다. 예를 들어 하나의 트랜잭션에서 여러 엔티티를 저장한다고 가정한다.

```java
EntityTransaction transaction = em.getTransaction();
transaction.begin();

em.persist(memberA);
em.persist(memberB);

transaction.commit();
```

JPA는 변경 작업을 관리하다가 DB와 동기화가 필요한 시점에 SQL을 실행할 수 있다. 이를 **트랜잭션을 지원하는 쓰기 지연(transactional write-behind)** 이라고 한다.

![쓰기 지연](image.png)

개념적으로 보면 영속성 컨텍스트에는 엔티티를 보관하는 1차 캐시와 함께 실행할 변경 작업을 관리하는 영역이 존재한다. 그래서 여러 변경을 트랜잭션이라는 하나의 작업 단위 안에서 다룰 수 있다.

다만 SQL 실행 시점이 항상 같은 것은 아니다. 예를 들어 `IDENTITY` 식별자 생성 전략은 DB INSERT 이후에 식별자를 얻을 수 있기 때문에 `persist()` 시점에 INSERT가 먼저 실행될 수 있다. 쓰기 지연은 SQL을 반드시 커밋까지 미룬다는 뜻이 아니라, **JPA가 트랜잭션 안에서 변경 작업과 실행 시점을 관리한다는 의미**로 보는 편이 정확하다.

## 4. 값을 바꾸기만 했는데 UPDATE가 실행되는 이유

JPA에서는 영속 상태의 엔티티를 수정하기 위해 별도의 `update()` 메서드를 호출하지 않는다.

```java
Member member = em.find(Member.class, "memberA");

member.setUsername("hi");
member.setAge(10);
```

이 코드에는 UPDATE를 요청하는 메서드가 없다. 그런데 DB와 동기화되는 시점이 오면 변경된 값이 반영될 수 있다. 영속성 컨텍스트가 엔티티를 관리하기 시작할 때의 상태를 **스냅샷(Snapshot)** 으로 보관하기 때문이다.

![스냅샷](<스크린샷 2026-08-20 150222.png>)

플러시가 발생하면 현재 엔티티의 값과 스냅샷을 비교한다. 값이 달라졌다면 JPA는 해당 엔티티가 변경되었다고 판단하고 필요한 UPDATE SQL을 생성한다. 이 동작을 **변경 감지(Dirty Checking)** 라고 한다.

결국 개발자는 영속 상태의 객체를 수정하고, 어떤 SQL이 필요한지는 영속성 컨텍스트가 엔티티의 상태 변화를 보고 결정한다.

## 5. 플러시는 언제 DB와 상태를 맞출까

영속성 컨텍스트가 관리하던 변경 내용을 DB와 동기화하는 과정이 **플러시(flush)** 다. 직접 `em.flush()`를 호출할 수도 있지만 일반적으로는 다음과 같은 시점에 플러시가 발생한다.

- `flush()`를 직접 호출할 때
- 트랜잭션을 커밋할 때
- 기본 flush 모드에서 현재 변경사항이 조회 결과에 영향을 주는 JPQL을 실행할 때

예를 들어 엔티티를 저장한 뒤 같은 트랜잭션에서 JPQL로 조회한다고 가정한다.

```java
em.persist(memberA);
em.persist(memberB);

List<Member> members = em.createQuery(
    "select m from Member m",
    Member.class
).getResultList();
```

아직 DB에 반영되지 않은 변경이 있는데 그대로 SELECT를 실행하면 영속성 컨텍스트가 알고 있는 상태와 DB 조회 결과가 달라질 수 있다. 기본 `FlushModeType.AUTO`에서는 쿼리 결과에 영향을 주는 변경사항이 있다면 필요한 동기화가 이루어진다.

여기서 플러시와 커밋은 구분해야 한다. **플러시는 변경 SQL을 DB에 전달해 상태를 동기화하는 과정이고, 커밋은 트랜잭션을 최종 확정하는 과정이다.** 플러시가 발생해도 영속성 컨텍스트가 비워지는 것은 아니며, 1차 캐시와 영속 상태의 엔티티는 그대로 유지된다.

> [!note] 쿼리 결과에 영향을 주는 변경
> JPQL 자체가 변경 쿼리라는 의미가 아니다. JPQL을 실행하기 전에 쌓인 변경사항이 SELECT 결과에 영향을 줄 수 있다는 의미다.

## 6. 정리

영속성 컨텍스트를 단순히 엔티티를 저장하는 공간으로 보면 1차 캐시, 쓰기 지연, 변경 감지, 플러시가 각각 별개의 기능처럼 보인다. 하지만 실제로는 모두 **엔티티의 상태를 관리하고 그 변화를 DB 작업으로 연결하는 하나의 흐름** 안에 있다.

- 영속성 컨텍스트가 엔티티를 관리한다.
- 관리 중인 엔티티는 1차 캐시에 보관된다.
- 처음 상태와 현재 상태를 비교해 변경을 감지한다.
- 필요한 변경 작업을 관리하다가 플러시 시점에 DB와 동기화한다.

즉 영속성 컨텍스트의 핵심은 **엔티티의 상태를 추적하고, 객체의 상태 변화가 필요한 DB 작업으로 이어지도록 관리하는 것**이다.
