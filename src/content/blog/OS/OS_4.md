## 1. 직접 실행과 운영체제의 제어

CPU 가상화는 여러 프로세스가 각자 CPU를 사용하는 것처럼 실행되게 만드는 기술이다. 운영체제가 프로그램의 명령을 하나씩 대신 해석하면 제어하기는 쉽지만 실행 비용이 커진다. 실제 운영체제는 사용자 프로그램의 명령을 가능한 한 CPU에서 직접 실행한다.

직접 실행만 허용하면 두 가지 문제가 생긴다.

* 프로그램이 디스크, 메모리와 장치에 제한 없이 접근할 수 있다.
* 프로그램이 CPU를 계속 사용하면 운영체제가 다른 프로세스로 전환할 수 없다.

**제한적 직접 실행(Limited Direct Execution)** 은 프로그램을 CPU에서 직접 실행하되, 하드웨어가 실행 권한과 제어 이동 경로를 제한하는 방식이다. 프로그램은 빠르게 실행되고 운영체제는 시스템 자원과 CPU 스케줄링에 대한 제어권을 유지한다.

## 2. 사용자 모드와 커널 모드

CPU는 실행 권한이 다른 모드를 제공한다. 구체적인 명칭과 단계는 아키텍처마다 다를 수 있지만, 운영체제 개념에서는 사용자 모드와 커널 모드로 구분할 수 있다.

### 2.1 사용자 모드

일반 애플리케이션은 사용자 모드에서 실행된다. 사용자 모드의 코드는 자신의 명령을 CPU에서 직접 실행할 수 있지만, 시스템 전체에 영향을 주는 특권 명령은 실행할 수 없다.

대표적으로 다음 작업은 운영체제의 중재가 필요하다.

* 장치에 직접 명령을 내리는 작업
* 페이지 테이블처럼 메모리 보호에 영향을 주는 상태 변경
* 인터럽트 타이머를 설정하거나 중지하는 작업
* 다른 프로세스의 주소 공간과 운영체제 메모리에 접근하는 작업

사용자 모드는 입출력 기능을 전혀 사용할 수 없는 모드가 아니다. 애플리케이션은 운영체제가 제공하는 시스템 콜을 통해 파일과 네트워크를 사용할 수 있다.

### 2.2 커널 모드

운영체제 커널은 커널 모드에서 특권 명령과 보호된 자원에 접근한다. 그렇다고 사용자 프로그램이 원하는 주소로 바로 커널 모드에 진입할 수 있는 것은 아니다. 하드웨어와 운영체제가 미리 정한 진입점으로만 제어를 이동해야 한다.

운영체제는 부팅 과정에서 시스템 콜, 예외와 인터럽트를 처리할 커널 진입점을 설정한다. 사용자 프로그램은 이 진입점 자체를 임의로 변경할 수 없다.

## 3. 시스템 콜은 어떻게 커널로 제어를 넘길까?

애플리케이션이 파일을 읽으려면 운영체제에 작업을 요청해야 한다. C 코드에서 `read()`나 `open()`이 일반 함수처럼 보이더라도, 라이브러리 함수 내부에서는 시스템 콜 번호와 인자를 준비하고 아키텍처가 제공하는 특수 명령으로 커널에 진입한다.

```text
사용자 프로그램
→ 라이브러리 함수가 시스템 콜 인자 준비
→ 시스템 콜 진입 명령 실행
→ CPU가 현재 사용자 문맥 저장
→ 커널 모드로 전환
→ 미리 등록된 시스템 콜 처리기로 이동
→ 커널이 인자와 권한 검증 후 작업 수행
→ 반환값과 사용자 문맥 복원
→ 사용자 모드의 다음 명령부터 실행
```

시스템 콜은 운영체제 함수를 일반 함수처럼 직접 호출하는 과정이 아니다. 권한 수준을 바꾸고 정해진 커널 코드로 이동하는 **보호된 제어 이동**이다. 커널은 사용자로부터 받은 주소, 크기와 파일 디스크립터를 신뢰하지 않고 검증해야 한다.

## 4. 시스템 콜, 예외와 인터럽트의 차이

세 경우 모두 실행 중인 사용자 프로그램에서 커널로 제어가 이동할 수 있지만 발생 원인은 다르다.

<!-- table-caption: 커널로 제어가 이동하는 사건 비교 -->

| 구분 | 발생 시점 | 발생 원인 | 예시 |
| --- | --- | --- | --- |
| 시스템 콜 | 현재 명령과 동기적 | 프로그램이 운영체제 서비스를 의도적으로 요청 | 파일 읽기, 프로세스 생성 |
| 예외 | 현재 명령과 동기적 | 명령 실행 중 오류나 특별한 조건 발생 | 0으로 나누기, 잘못된 메모리 접근 |
| 인터럽트 | 현재 명령과 비동기적 | CPU 외부 장치나 타이머가 사건을 알림 | 타이머 만료, 입출력 완료 |

예외가 발생했다고 항상 프로세스가 종료되는 것은 아니다. 커널이 처리할 수 있는 예외라면 복구하거나 신호를 전달할 수 있다. 잘못된 메모리 접근처럼 계속 실행하기 어려운 경우에는 해당 프로세스를 종료할 수 있다.

## 5. 타이머 인터럽트는 어떻게 CPU를 되찾을까?

프로세스가 자발적으로 시스템 콜을 호출하거나 대기 상태로 들어가야만 운영체제가 CPU를 되찾을 수 있다면, 무한 반복하는 프로그램은 CPU를 계속 차지할 수 있다. 현대 운영체제는 타이머 인터럽트를 이용해 프로세스의 협조 없이도 제어권을 회수한다.

운영체제는 프로세스를 실행하기 전에 하드웨어 타이머를 설정한다. 일정 시간이 지나면 타이머가 인터럽트를 발생시키고 CPU는 현재 사용자 문맥을 저장한 뒤 커널의 인터럽트 처리기로 이동한다.

```text
프로세스 A 실행
→ 타이머 인터럽트 발생
→ A의 사용자 문맥 저장
→ 커널 모드로 전환
→ 스케줄러가 실행할 프로세스 결정
→ 필요하면 A의 문맥을 PCB에 저장
→ 프로세스 B의 문맥 복원
→ 사용자 모드에서 B 실행
```

이 방식은 프로세스가 CPU 반환에 협조하지 않아도 운영체제가 실행 시간을 나눌 수 있는 **선점형 스케줄링**의 기반이다. 타이머를 설정하고 인터럽트 처리를 구성하는 작업은 시스템 제어에 직접 영향을 주므로 커널만 수행한다.

## 6. 문맥 교환에서 무엇을 저장할까?

스케줄러가 다른 프로세스를 선택하면 운영체제는 현재 프로세스의 실행 상태를 저장하고 선택된 프로세스의 상태를 복원한다. 이를 문맥 교환이라고 한다.

보존해야 할 정보에는 프로그램 카운터, 스택 포인터와 일반 레지스터 등이 포함된다. 운영체제는 이 문맥을 PCB와 커널 스택 같은 커널 자료 구조에 관리한다. 문맥 교환이 끝나면 새 프로세스는 이전에 중단된 명령 위치에서 실행을 이어간다.

시스템 콜이나 타이머 인터럽트가 발생했다고 항상 다른 프로세스로 전환되는 것은 아니다. 커널이 현재 요청을 처리한 뒤 같은 프로세스로 돌아갈 수도 있다. **커널 진입**과 **문맥 교환**은 관련 있지만 같은 동작은 아니다.

## 7. 제한적 직접 실행의 비용과 경계

제한적 직접 실행은 사용자 프로그램을 네이티브 CPU에서 실행하므로 효율적이다. 다만 시스템 콜, 인터럽트와 문맥 교환에는 모드 전환과 상태 저장·복원 비용이 발생한다.

운영체제는 모든 명령에 개입하지 않고 다음 경계에서만 제어한다.

* 프로그램이 보호된 서비스를 요청할 때
* 예외가 발생했을 때
* 장치나 타이머 인터럽트가 발생했을 때
* 스케줄러가 다른 프로세스를 실행하기로 결정했을 때

핵심은 직접 실행을 없애는 것이 아니라 **어떤 작업을 직접 실행하도록 허용하고 어떤 시점에 운영체제가 개입할지를 하드웨어와 함께 설계하는 것**이다.

## 8. 정리

* 제한적 직접 실행은 프로그램을 CPU에서 직접 실행하면서도 운영체제가 자원과 CPU에 대한 제어권을 유지하는 방식이다.
* 사용자 프로그램은 사용자 모드에서 실행되며 보호된 작업은 시스템 콜을 통해 커널에 요청한다.
* 시스템 콜과 예외는 현재 명령에 동기적으로 발생하고, 하드웨어 인터럽트는 외부 사건에 의해 비동기적으로 발생한다.
* 타이머 인터럽트는 운영체제가 프로세스의 협조 없이 CPU를 회수하고 선점형 스케줄링을 수행하게 한다.
* 커널 진입이 항상 문맥 교환을 의미하지는 않으며, 스케줄러가 다른 프로세스를 선택할 때 문맥 교환이 발생한다.
